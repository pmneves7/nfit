# node23 cached-bin save stall

## Diagnosis and live recovery

The nfit 0.97.5 process (PID 3164807) on analysis-node23 stopped responding
after a cache export destination was selected and confirmed. Initial checks
around 2026-09-19 01:22 UTC found:

- Roughly 170 GiB available node memory and almost no active swap traffic.
- nfit RSS about 102.7 GiB, with about 72 MiB swapped out.
- No output archive descriptor, no advancing write counters, and unchanged
  thread CPU times across a nine-second sample. The main thread slept in
  `hrtimer_nanosleep`.
- A `QFileInfoGather` thread, indicating a Qt file chooser had been created.

The SSH alias reached node21; node23 diagnostics were collected in a separate
terminal through the existing ThinLinc session. Debugger attachment was denied
by the host, so no Python/native backtrace was available.

The shared `~/.config/QtProject.conf.lock` dated from September 11 and named
nfit PID 4026892 on node23. A direct `/proc` check on **node23**, not node21,
confirmed that owner no longer existed. Its boot identifier matched node23.
The exact lock contents and ownership were checked again before it was renamed
to `QtProject.conf.lock.stale-20260919-4026892`, preserving a recovery backup.
No active lock, settings contents, project data, or nfit process was removed.

Immediately afterward, QtProject.conf was updated at 01:32:24 UTC and the
same nfit process began writing an NPZ. At 01:33:33 its `wchar` counter had
increased from about 49.7 MB to 2.05 GB. The export completed at 01:34:19:

- File: `YMn2_22_meV_sample_Fd-3m_symmetry.npz`.
- Actual chosen directory: `/SNS/users/paulneves/data/SNS/CORELLI/IPTS-32964/shared/nfit`.
  This differs from the SEQUOIA folder recalled in the report; the open file
  descriptor and Qt's saved directory history both identified CORELLI.
- Archive size: **3,119,201,135 bytes**.
- ZIP central directory readable: **48 members**, **21,698,429,916 uncompressed
  bytes**. This was a metadata check, not a full decompression/CRC validation.

At 01:36:38 the process was actively writing another NPZ under its own
`/tmp/nfit-binning-cache-*` directory, used by project-save serialization.
Its cumulative CPU time advanced 25 seconds in a three-second wall interval,
and written bytes had reached 7.57 GB. Thus the initial idle stall was
released; subsequent GUI unresponsiveness can be active synchronous project
saving. The investigation did not cancel, restart, or inject code into nfit.

At 01:42 UTC the nfit window had repainted and displayed active rebin progress.
There were no archive output descriptors in the final process sample. Zenity's
installed help confirmed support for save, directory and overwrite-confirmation
options on node23.

## Cause and prevention

Qt's widget file chooser saves its own history and layout through a separate
`QtProject` QSettings store. This is outside nfit's existing lock-free Linux
preferences store. See Qt's [QFileDialog source](https://raw.githubusercontent.com/qt/qtbase/6.8/src/widgets/dialogs/qfiledialog.cpp),
`QFileDialogPrivate::saveSettings`. The settings-lock wait explains why
confirming a destination did not reach the NPZ writer. Moving the verified
stale lock and observing the same process resume writing provides stronger
causal evidence than the initially suspected hidden-window explanation.

The 0.98.2 fix extends the existing Linux Zenity/Yad path from opening files
to saving files and selecting directories. These paths do not construct a
Qt file chooser and therefore avoid its QtProject settings persistence.
Default filenames, translated filters, remembered directories, overwrite
confirmation and cancellation are preserved. The raised Qt chooser remains a
fallback when no working GTK helper is available; that fallback retains Qt's
settings behavior. The 3D isosurface export also retains Qt because its caller
uses the selected format filter, which GTK helpers cannot return. No global
settings path or lock-removal policy was added.

The cache export chooser also now uses its active modal parent, correcting a
separate parenting issue. Cache serialization and project saves still perform
synchronous work on the GUI thread; making those operations asynchronous is
separate work and is not claimed as fixed here.

## Validation

Focused file-dialog, preference, packaging and volume-viewer tests passed
(50 tests), along with five cache-prompt integration tests. Ruff, byte compilation, Sphinx with
warnings treated as errors, and diff checks passed. The running installed
application was not replaced; the live recovery used only the verified stale
lock rename. The backup lock remains available. Temporary diagnostic logs were
collected locally and removed from the remote shared home directory.
